Server Action의 이해

October 19, 2026

들어가며

Server Action 을 매일 쓰고 있었지만, 자세한 사용법과 왜 지금 Next.js에서 많이 사용되었는지 그것에 대해서 적어 볼려고 합니다.

  • 왜 나왔고, 왜 다들 쓰는가
  • 서버에서 실행되는데, 왜 서버가 아닌가
  • 메모리와 CPU 는 언제 할당받고, 언제 돌려주는가
  • 동기와 비동기가 섞이면 어떻게 되는가

공식 문서와 실제 코드를 같이 보면서 하나씩 답해 본 기록입니다.

기준 버전은 Next.js 16, React 19 입니다. 아래 코드는 이해를 돕기 위해 만든 예시입니다.

1. 출시 이유

시점일
2020-12React 팀이 React Server Components 공개
2023-03서버 데이터 읽기는 정리됨. 반대 방향인 클라이언트 → 서버 변경(mutation)을 탐색 중
2023-05Next.js 13.4 에서 Server Actions Alpha. "중간 API 레이어 없이 함수를 직접 호출"
2023-10Next.js 14 에서 Stable
2024-12React 19 가 Actions 를 정식화. useActionState, useFormStatus, useOptimistic, <form action={fn}>

이전에는 저장 버튼 하나를 만들 때마다 같은 일을 반복했습니다. 서버에 API 주소를 만들고, 화면에서 fetch 로 부르고, JSON 으로 바꿔 보내고, 응답을 풀고, 저장이 끝나면 바뀐 데이터를 다시 불러와 화면을 갱신했습니다. 대부분이 기능과 상관없는 반복이고, 화면과 서버의 형식을 사람이 맞추다 보니 한쪽만 바뀌어 어긋나기도 했습니다.

예전Server Action
API Route 를 따로 만들고 URL·메서드·요청/응답 형식을 설계함수에 'use server' 만 붙이면 프레임워크가 통로를 만듦
fetch + useState 로 로딩·에러 상태 관리useActionState 가 [state, action, pending] 제공
저장 후 화면 데이터를 다시 fetch응답 하나에 반환값과 새 화면 데이터가 함께 옴
서버 필드 이름이 바뀌면 실행해 봐야 오류를 앎같은 함수를 import 하므로 타입이 공유되어 컴파일 단계에서 잡힘
// actions.ts
'use server'

export async function saveSettings(input: SettingsInput) {
  // 서버에서만 실행된다
}
// 화면
import { saveSettings } from './actions'

<button onClick={()=> saveSettings(form)}>저장</button>

화면에서는 그냥 함수를 부르는 것처럼 보입니다.

2. 실제로는 POST 요청 하나

그런데 브라우저와 서버는 다른 컴퓨터라서, 함수를 정말 직접 부를 수는 없습니다. Next.js 가 중간에서 일을 대신합니다.

  1. 빌드할 때 클라이언트 번들의 함수 본문을 "액션 ID + 호출 장치"로 바꿉니다.
  2. 버튼을 누르면 POST 요청이 나갑니다.
  3. 서버는 요청에 담긴 ID 로 어떤 함수인지 찾아 실행합니다.
  4. 결과와 바뀐 화면 데이터를 함께 돌려줍니다.
[브라우저] 버튼 클릭
   → POST /settings               ← 페이지 URL
     header: next-action: 7f3a…   ← 어떤 함수인지
     body: 인자
   → [Next 서버 프로세스] ID 로 함수를 찾아 실행 → 결과 + 새 화면 데이터

주소는 그 액션을 쓰는 페이지 주소이고, 어떤 함수인지는 next-action 헤더의 ID 로 구분합니다. 저장·수정·삭제처럼 바꾸는 일 전용이라 POST 만 씁니다. 조회는 Server Component 가 화면을 그릴 때 합니다.

그래서 저는 Server Action 을 "엔드포인트를 직접 만들지 않는 API" 로 이해했습니다.

REST API 와 무엇이 다른가

REST APIServer Action
약속주소와 요청 형식을 직접 설계함수 이름과 인자가 곧 약속
쓰는 곳앱·웹·외부 시스템 등 여러 곳그 Next.js 앱의 화면
약속 공유문서TypeScript 타입

여러 곳이 함께 쓰는 고정된 기능은 REST API, 한 화면에서만 쓰는 저장 기능은 Server Action 이 잘 맞습니다.

3. 서버에서 돌지만, 서버는 아님

"서버"는 포트를 열고 계속 떠 있으면서 요청을 기다리는 프로그램입니다. Spring 으로 치면 java -jar app.jar 로 띄운 애플리케이션 자체입니다. Server Action 은 그 서버가 아니라 서버 안에서 실행되는 함수 하나입니다. Spring 으로 치면 @PostMapping 이 붙은 컨트롤러 메서드에 가깝습니다.

SpringNext.js
Spring Boot 애플리케이션 (서버)Next 서버 프로세스
@PostMapping("/settings") 메서드'use server' 함수
URL 을 개발자가 정함URL·ID 를 컴파일러가 정함

서버라고 부르지 않는 이유는 네 가지입니다.

  1. 자기 프로세스가 없습니다. 따로 떠 있지 않고, Next 서버가 요청을 받으면 불려서 실행되고 끝납니다.
  2. 자기 자원이 없습니다. 메모리·CPU·DB 연결 풀을 Next 서버와 함께 씁니다. 그래서 액션 하나가 무거운 계산을 하면 다른 요청까지 멈춥니다.
  3. 고정된 주소가 없습니다. ID 가 빌드마다 바뀔 수 있어서, 앱이나 외부 시스템이 API 처럼 부를 수 없습니다.
  4. 자기 화면에 묶여 있습니다. 그 앱의 폼·버튼에서 부르라고 만든 통로입니다.

정리하면 Server Action 은 "서버 안에서 도는 함수에, 프레임워크가 호출 통로를 자동으로 붙여 준 것" 입니다.

그런데 주소가 숨겨져 있을 뿐 실제로는 HTTP 요청입니다. 누구나 요청을 보낼 수 있습니다. 이 점이 뒤에서 말할 주의할 점으로 이어집니다.

4. 동기와 비동기 ① — 화면에서 부를 때

Server Action 호출은 항상 비동기입니다. Promise 를 돌려주기 때문에 await 로 기다립니다. 기다리는 동안 화면은 멈추지 않으니, useTransition 의 isPending 으로 버튼을 잠시 막아 두 번 누르는 걸 방지합니다.

const [isPending, startTransition] = useTransition()

<button
  disabled={isPending}
  onClick={()=> startTransition(async ()=> { await saveSettings(form) })}
>
  저장
</button>

재미있는 점은, 여러 액션을 Promise.all 로 동시에 불러도 브라우저에서는 하나씩 차례로 보낸다는 것입니다. 응답마다 바뀐 화면 데이터가 같이 오기 때문에, 순서가 섞여서 옛 응답이 새 화면을 덮지 않도록 줄을 세운다고 이해했습니다.

다만 공식 문서는 이 순차 실행을 "구현 세부사항이며 바뀔 수 있다"고 적고 있습니다. 데이터 정합성은 이 동작에 기대지 말고 DB 트랜잭션과 제약 조건으로 지켜야 합니다. 같은 이유로 조회를 액션으로 하면 안 됩니다. 줄을 서서 직렬로 실행되기 때문입니다.

5. 동기와 비동기 ② — 서버에서 실행될 때

서버는 여러 사용자의 액션을 줄 세우지 않고 받는 대로 동시에 실행합니다. 그런데 JS 코드를 실행하는 스레드는 하나입니다.

  • await 로 DB 를 기다리는 동안에는, 스레드가 쉬지 않고 다른 액션을 실행합니다. I/O 위주라면 스레드 하나로도 동시성이 높습니다.
  • 반대로 10만 행을 가공하는 동기 계산을 하면, 스레드가 그 일에 묶여서 그동안 모든 요청이 멈춥니다.
상황결과대응
await 로 DB·fetch 대기그동안 다른 요청 처리그대로 OK
대용량 JSON.parse, 동기 압축·암호화, O(n²) 루프모든 동시 요청이 멈춤잘게 쪼개거나 워커·별도 작업으로
한 액션 안의 독립적인 조회 여러 개순차 await 면 느림액션 안에서 Promise.all
await 없이 던져 놓은 Promise유실되거나, reject 시 프로세스가 죽을 수 있음after() 사용
다른 사용자의 같은 데이터 수정await 지점마다 섞여 실행트랜잭션·잠금·제약 조건
같은 트랜잭션 안의 쿼리를 Promise.all드라이버가 직렬 처리하거나 오류트랜잭션 안은 순차 await

관계없는 조회를 액션 안에서 Promise.all 로 바꿔 직접 측정해 보니 408ms 가 203ms 로 줄었습니다.

'use server'
import { after } from 'next/server'

export async function saveSettings(input: SettingsInput) {
  const [settings, schedule] = await Promise.all([
    getSettings(input.id),   // 서로 관계없는 조회는 동시에
    getSchedule(input.id),
  ])

  // ... 저장

  after(() => sendNotification(input.id)) // 응답 뒤에 해도 되는 일
}

기다리는 일은 await 에 맡기고, 오래 걸리는 계산은 액션 밖으로 뺍니다.

6. 한 번의 생명주기 — 메모리와 CPU

Server Action 한 번이 메모리와 CPU 를 어떻게 쓰는지 다섯 단계로 정리했습니다.

  1. 요청이 도착하면 본문을 풀어 인자 복사본을 메모리에 만듭니다. 큰 데이터를 인자로 보내면 안 되는 이유이고, 기본 본문 한도도 1MB 입니다.
  2. 실행 중에는 스레드 하나에서 코드가 돌고, 객체와 DB 결과가 힙에 생깁니다. 여기서 긴 동기 계산을 하면 다른 요청이 멈춥니다.
  3. await 하는 동안 만든 객체는 메모리에 남아 있지만, CPU 는 다른 요청을 실행합니다.
  4. 응답할 때 반환값을 다시 직렬화해 보냅니다. 큰 결과를 반환하면 그만큼 메모리를 더 씁니다.
  5. 끝나면 아무도 참조하지 않는 객체를 GC 가 회수합니다.

Server Action 은 자기 자원 없이 Next.js 서버의 메모리와 스레드를 빌려 쓰고, 응답이 끝나면 돌려줍니다.

조심할 것

  • 모듈 레벨 변수는 요청이 끝나도 남고, 모든 사용자가 공유합니다. DB 연결 풀처럼 일부러 공유하는 것은 괜찮지만, 요청 데이터를 넣으면 다른 사용자에게 노출되고, 크기 제한 없는 캐시는 메모리 누수가 됩니다.
  • GC 는 JS 힙만 관리합니다. 이미지 처리 같은 네이티브 라이브러리가 잡은 메모리는 GC 밖에 있습니다. 메모리 그래프에서 heapUsed 는 평평한데 rss 만 늘면 네이티브 쪽을 의심해야 합니다.

7. Server Action 을 쓸 때 지키는 순서

함수처럼 보이지만 공개된 입구라서, 저는 다섯 단계 순서를 지킵니다.

'use server'

export async function updateSettings(formData: FormData) {
  // ① 입력 검증(스키마 검증) — 인자는 적대적이라고 본다
  const input = schema.parse(Object.fromEntries(formData))

  // ② 권한 확인 — 페이지의 인증 검사가 액션까지 지켜 주지 않는다
  const session = await requireSession()
  await assertCanEdit(session, input.id) // ID 만 받고 소유권은 세션 기준으로 다시 확인

  // ③ 저장 — 트랜잭션 하나로, 하나라도 실패하면 전부 롤백
  await db.transaction(async (tx) => {
    await tx.update(settings).set(input.settings).where(eq(settings.id, input.id))
    await tx.delete(schedules).where(eq(schedules.settingsId, input.id))
    await tx.insert(schedules).values(input.schedules)
  })

  // ④ 화면 갱신
  revalidatePath('/settings')

  // ⑤ 이동 — 마지막에, try/catch 밖에
  redirect('/settings')
}
단계안 하면
① 입력 검증이상한 값이 DB 까지 들어감
② 권한 확인버튼을 숨겨도 누구나 POST 해서 남의 데이터를 수정할 수 있음
③ 트랜잭션 저장중간에 실패하면 일부만 저장된 채 남음
④ 화면 갱신저장됐는데 화면은 옛날 값
⑤ redirect 위치redirect() 는 내부적으로 에러를 던져서, catch 에 잡히면 이동이 안 됨

이 밖에 기억할 것들입니다.

  • 반환값은 화면에 필요한 것만. 반환값도 직렬화되어 클라이언트로 갑니다. DB 행을 통째로 돌려주지 않습니다.
  • 인자·반환값은 직렬화 가능해야 합니다. 클래스 인스턴스, 일반 함수, 이벤트 객체는 안 됩니다.
  • redirect() 를 꼭 try 안에 둬야 한다면 catch 에서 다시 던집니다(unstable_rethrow). notFound() 도 같습니다.

8. 배포 직후에 깨지는 버튼

action ID 는 빌드마다 바뀔 수 있습니다. 배포 전에 열어 둔 화면에서 버튼을 누르면, 새 서버에는 그 ID 가 없어서 Failed to find Server Action 에러가 납니다.

서버가 여러 대라면 NEXT_SERVER_ACTIONS_ENCRYPTION_KEY 를 고정해서 빌드·인스턴스가 바뀌어도 ID 가 유지되게 합니다. 그런데 키를 고정해도 안심할 수 없었습니다. ID 는 파일 경로, export 이름, 파라미터 개수에도 영향을 받습니다. 실제로 액션을 옮긴 뒤 배포하자, 열려 있던 화면의 일괄 저장이 이 에러로 실패한 적이 있습니다.

그래서 지금은 이렇게 하면서 ID 변경으로 실패를 방지했습니다.

  • 액션을 옮기거나 이름·파라미터를 바꿀 때는 새 액션을 더하고 옛 export 를 한 릴리스 동안 남겨 둡니다.
  • 파일 안에 인라인으로 쓴 'use server' 는 파일 안 순번으로 ID 가 정해져서, 앞에 하나를 더하면 뒤의 ID 가 바뀝니다.
  • 사용자 입장에서는 새로고침하면 새 ID 를 받아 다시 동작하니, 실패 시 새로고침을 안내하는 UI 를 둡니다.

마치며

한 문장으로 정리하면, Server Action 은 호출 통로가 붙은 서버 함수입니다.

  • 함수 호출처럼 보이지만 실제로는 POST 요청과 ID 다.
  • 화면은 await 로 기다리고, 서버는 스레드 하나를 모든 요청이 나눠 쓴다.
  • 메모리와 CPU 는 서버 것을 빌려 쓰고 돌려준다.
  • 누구나 부를 수 있는 입구라서 검증 → 권한 → 저장 → 갱신 → 이동 순서를 지킨다.
