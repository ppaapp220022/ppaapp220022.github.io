Next.js 공식 학습 과정 완주 후기

September 22, 2026

왜 지금 이 과정을 들었나

이 블로그 자체가 Next.js 로 만들어져 있습니다. 그런데 저는 Spring Boot 로 백엔드를 배운 사람이라, Next.js 코드를 보면 "이건 Controller 인가, 아닌가", "이 함수는 어디서 실행되나" 같은 질문이 계속 걸렸습니다. 템플릿을 가져다 쓰면서도 app/ 폴더 안의 파일들이 각각 무슨 역할인지 제대로 이해하지 못한 채 고치고 있었습니다. 감으로 넘기지 않으려면 프레임워크를 만든 쪽이 쓴 공식 학습 과정 을 처음부터 끝까지 따라 하는 게 가장 빠른 길이었습니다.

9월 11일에 화면부터 서버 운영까지 한 번 훑으며 개념 노트를 만들고, 9월 14일에 과정을 완주했습니다. 이 글은 그 두 기록을 합친 것입니다.

과정 구성

강좌는 가상의 회사 대시보드를 만들면서 진행됩니다. 송장과 고객 목록을 보여 주고, 검색과 페이지네이션을 붙이고, 추가·수정·삭제하고, 마지막에 로그인까지 넣습니다. 총 16장이고 각 장 끝에 짧은 퀴즈가 있습니다.

크게 세 덩어리로 나뉩니다.

  • 1~5장: 구조와 화면. 폴더가 곧 URL 이 되는 라우팅, layout.tsx 와 page.tsx 의 역할 분담, next/font 와 next/image 최적화, <Link> 로 전체 새로고침 없이 이동하기.
  • 6~10장: 데이터와 렌더링. 서버 컴포넌트에서 DB 를 바로 조회하기, 정적 렌더링과 동적 렌더링의 차이, loading.tsx 와 <Suspense> 로 느린 부분만 나중에 채우는 스트리밍, 부분 사전 렌더링.
  • 11~16장: 상호작용과 마무리. 검색어를 URL 쿼리에 담기, 서버 액션으로 폼 처리하기, error.tsx 와 notFound(), 접근성, NextAuth 인증, metadata 설정.

자주 틀렸던 개념 7가지

과정을 따라 하면서 "그런 줄 알았는데 아니었다" 싶은 지점을 복습 질문 형태로 남겼습니다. 답은 전부 "아니다" 입니다.

  1. 'use client' 가 있으면 서버에서 실행되지 않는가? 아니다. Client Component 도 첫 접속 때는 서버에서 HTML 로 미리 렌더링된다. 'use client' 는 "브라우저 코드의 진입 경계" 표시이지 "서버 금지" 표시가 아니다.
  2. 'use server' 가 없으면 서버에 접근할 수 없는가? 아니다. 서버 컴포넌트에서 DB 를 조회하거나 Route Handler 에서 처리할 때는 이 선언이 필요 없다. 클라이언트가 네트워크로 호출할 서버 함수를 만들 때만 붙인다.
  3. 서버 액션 요청에 DB 코드가 실려 가는가? 아니다. 함수는 서버에 배포돼 있고, 브라우저는 함수 식별 정보와 입력값만 POST 로 보낸다. 클라이언트가 임의의 함수 이름을 보내 아무거나 실행하는 구조가 아니다.
  4. POST 만으로 삭제하려면 DELETE 요청을 한 번 더 보내야 하는가? 아니다. HTTP 메서드와 DB 명령은 별개다. POST 로 서버의 삭제 함수를 호출하면 그걸로 끝이다. 별도 백엔드가 있어서 POST → Next.js → DELETE API → 백엔드 가 되는 건 백엔드를 분리했기 때문이지 POST 의 제약 때문이 아니다.
  5. 서버 액션이면 인증·인가를 생략해도 되는가? 아니다. 숨겨진 <input type="hidden"> 도 클라이언트 입력이다. Controller 를 안 쓴다고 검증이 사라지는 게 아니라, 요청 수신과 함수 연결 코드를 대신 써 주는 것뿐이다.
  6. 서버리스는 서버가 없는가? 아니다. 실행 환경의 배정·확장·복구를 플랫폼에 위임하는 것이다. 서버 액션을 쓰는지와 서버리스인지는 별개의 선택이다.
  7. 별도 백엔드를 없애면 백엔드 역할도 없어지는가? 아니다. 구성도에서 상자가 하나 줄어들 뿐, 입력 검증·권한 확인·업무 규칙은 Next.js 안으로 옮겨 간다.

Spring Boot 와 나란히 놓고 보기

제게 가장 도움이 된 건 익숙한 구조에 대응시켜 보는 것이었습니다.

Spring Boot  : 요청 → Controller → 업무 로직 → DB
Server Action: 요청 → Next.js 가 함수 연결 → 업무 로직 → DB
Route Handler: 요청 → GET·POST 등의 핸들러 → 업무 로직 → DB

이렇게 놓고 나니 언제 무엇을 쓰는지가 정리됐습니다.

상황쓸 것
Next.js 화면의 제출·수정·삭제Server Action
모바일 앱이나 외부 서비스가 호출할 HTTP APIRoute Handler 또는 별도 백엔드
페이지에 필요한 데이터 조회Server Component 에서 서버 데이터 계층 직접 호출

revalidatePath 도 처음엔 DB 를 갱신하는 함수인 줄 알았는데, 해당 경로의 Next.js 캐시를 무효화하는 것뿐입니다. 별도 백엔드가 자기 캐시를 갖고 있다면 그건 따로 지워야 합니다.

느낀 점

  • "어디서 실행되는가" 를 파일 단위로 정한다. 기본은 전부 서버이고, 상태나 이벤트가 필요한 파일에만 'use client' 를 붙인다. 이 구분이 잡히니 코드를 읽을 때 항상 실행 위치부터 보게 됐다.
  • URL 을 상태 저장소로 쓴다. 검색어와 페이지 번호를 URL 에 두면 새로고침해도 유지되고 공유도 되고 서버 컴포넌트가 바로 읽는다.
  • 아쉬운 점. 강좌가 Vercel 배포와 Postgres 를 전제로 진행된다. 이 블로그처럼 정적 사이트로 내보내는 경우엔 서버 액션과 동적 렌더링을 못 쓰므로 그 차이를 따로 정리해야 했다.

다음에 할 것

  • 완주하고도 정리 노트를 며칠 미뤘더니 세부 내용이 벌써 흐릿해졌다. 다음 학습부터는 끝낸 날 바로 쓴다.
