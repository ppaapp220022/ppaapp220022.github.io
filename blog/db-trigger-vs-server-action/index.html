서버 액션과 DB 트리거, 같은 일을 해도 같은 코드가 아니다

October 15, 2026

들어가며

저는 DB 에 값을 채우는 로직이라면 서버 액션에 두든 DB 트리거에 두든 결과만 같으면 된다고 생각했습니다. 같은 행에 같은 값이 들어가니까요.

그 생각으로 트리거를 넣는 PR 을 올렸습니다. 피드백을 받고 그 PR 을 닫았고, 고치는 방향도 피드백을 따라 바꿨습니다. 이 글은 그 과정에서 알게 된 서버 액션과 DB 트리거의 차이에 대한 기록입니다.

실제 작업은 회사 코드라서, 아래 테이블·열·값은 이해를 돕기 위해 만든 예시입니다.

계기 — 라이브러리가 값을 안 보내기 시작했다

인증 라이브러리를 새 버전으로 올렸더니 소셜 로그인으로 가입하는 순간 DB 가 거절했습니다. PostgreSQL 의 23502, NOT NULL 위반이었습니다.

예시로 바꾸면 이런 상황입니다. 계정 테이블에 "어디서 가입했는지"를 적는 origin 열이 있고, NOT NULL 이 걸려 있습니다.

create table accounts (
  id          bigint primary key,
  provider    text not null,   -- 'google', 'github', 'email' ...
  external_id text not null,
  origin      text not null    -- 예전 버전 라이브러리가 채우던 값
);

예전 버전의 라이브러리는 origin 을 채워서 보냈습니다. 그런데 새 버전은 이 값을 더 이상 보내지 않습니다. 라이브러리 쪽에서 그 스펙을 되돌렸고, 릴리스 노트에는 "이 열의 NOT NULL 을 풀어 달라"는 안내가 있었습니다.

라이브러리(새 버전) ──insert(origin 없음)──▶ accounts.origin NOT NULL ──▶ 23502 ❌

라이브러리는 "이제 이 값은 안 쓴다"고 하고, DB 는 "이 값 없으면 못 받는다"고 버티는 상황이었습니다.

내가 고른 방법 — 트리거로 조용히 채우기

제가 처음 떠올린 건 트리거였습니다. origin 이 비어서 들어오면 DB 가 insert 직전에 예전 값으로 채워 넣는 방식입니다.

create function fill_account_origin() returns trigger
language plpgsql
as $$
begin
  if new.origin is null then
    new.origin := case new.provider
      when 'email' then 'local'
      else 'oauth:' || new.provider
    end;
  end if;
  return new;
end
$$;

create trigger fill_account_origin
  before insert on accounts
  for each row execute function fill_account_origin();

그때 제 눈에는 장점만 보였습니다.

  • 열도, 제약도, 고유 키도 그대로라 앱 코드를 하나도 안 바꿔도 된다.
  • 예전처럼 값을 보내는 쓰기는 그대로 통과하니, 배포 순서를 신경 쓰지 않아도 된다.
  • 테스트도 붙였고, 실패하던 테스트가 전부 초록이 됐다.

"앱은 건드리지 않고 DB 에서 조용히 해결한다." 저는 이 문장을 장점이라고 생각했습니다. 지금 보면 문제는 바로 그 "조용히"였습니다. 그리고 그걸 짚어 준 건 제가 아니라 팀의 피드백이었습니다.

받은 피드백 — 내 트리거가 남의 작업에서 실행된다

피드백의 요지는 이랬습니다.

우리는 기능을 나눠서 병렬로 작업한다. 트리거를 걸면, 그 테이블에 쓰는 다른 사람의 작업에서 네 로직이 실행된다. 그리고 그 사람은 자기 쿼리가 나갈 때 무엇이 같이 실행되는지 알 수 없다.

처음엔 잘 와닿지 않았습니다. 트리거는 마이그레이션 파일에 버젓이 적혀 있고, \d accounts 를 쳐 보면 누구나 확인할 수 있으니까요. 숨겨 놓은 게 아니라고 생각했습니다.

그런데 문제는 트리거가 있다는 걸 아느냐가 아니었습니다. 트리거가 언제, 누구의 작업에서 실행되고, 그때 무엇이 나가는지가 보이지 않는다는 점이었습니다. 저는 트리거를 만든 사람의 자리에서만 코드를 봤고, 그 트리거를 밟게 될 사람의 자리에는 서 보지 않았습니다.

1. 내가 만든 트리거가 다른 사람의 작업분으로 실행된다

예를 들어 다른 팀원이 "관리자 계정 일괄 등록" 기능을 만든다고 해 봅시다. 그 팀원은 자기 기능에 필요한 만큼만 accounts 에 insert 합니다.

// 다른 팀원의 작업분
await db.insert(accounts).values(
  admins.map((a) => ({ provider: 'admin', externalId: a.id })),
)

이 코드 어디에도 제 트리거는 없습니다. 그런데 DB 에 들어가는 순간 제 트리거가 실행되고, origin 에는 oauth:admin 이라는 엉뚱한 값이 채워집니다. 관리자 계정은 OAuth 로 가입한 적이 없는데도요.

  • 그 팀원의 PR 에는 흔적이 없다. diff 에는 insert 한 줄뿐이고, 리뷰어도 그 한 줄만 봅니다.
  • 트리거를 만든 저는 그 PR 의 리뷰어가 아니다. 병렬로 일하면 제가 모르는 기능이 제 트리거를 밟고 지나갑니다.
  • 각자의 테스트는 각자 초록이다. 값이 이상해도 에러가 나지 않으니, 누구의 테스트도 실패하지 않습니다.

2. 트리거가 발동할 때 어떤 쿼리가 나가는지 알 수 없다

호출하는 쪽에서 보이는 건 자기가 보낸 쿼리 한 줄입니다. 하지만 DB 안에서는 그보다 많은 일이 일어납니다.

-- 팀원의 코드가 보낸 쿼리 (로그에도 이것만 찍힌다)
insert into accounts (provider, external_id) values ('admin', 'a-001');

-- DB 안에서 실제로 일어나는 일
--   → fill_account_origin() 실행: new.origin := 'oauth:admin'
--   → 트리거가 더 있다면 그 안의 update·insert 도 같이

이번 트리거는 값 하나만 바꿨지만, 트리거 안에서 다른 테이블을 고치거나 기록을 남기기 시작하면 그 쿼리들도 전부 팀원의 insert 한 줄에 묻어 나갑니다. ORM 의 쿼리 로그에도, 앱 로그에도 보이지 않습니다. 느려지거나 락이 걸리거나 트리거 안에서 에러가 나도, 겉으로는 팀원의 insert 가 실패한 것처럼 보입니다.

사실 저도 한 번 걸렸습니다. 테스트 환경 중 하나가 트리거가 들어간 마이그레이션을 적용하지 않고 스키마를 만들고 있어서, 트리거를 넣었는데도 그 테스트는 계속 실패했습니다. 같은 insert 를 보내도 환경마다 실행되는 것이 달랐던 겁니다. 만든 당사자인 저조차 그걸 한 번에 알아보지 못했습니다.

서버 액션은 무엇이 다른가

같은 일을 서버 액션으로 하면 이렇게 됩니다.

'use server'

export async function createAccount(input: { provider: string; externalId: string }) {
  const origin = input.provider === 'email' ? 'local' : `oauth:${input.provider}`
  await db.insert(accounts).values({ ...input, origin })
}

하는 일은 트리거와 똑같습니다. 다른 건 읽는 사람이 어디서 출발하든 이 코드에 닿는다는 점입니다. 버튼에서 출발해도, 호출부에서 출발해도, oauth: 를 검색해도 이 함수가 걸립니다. 값을 정하는 판단과 그 판단이 일어나는 순간이 같은 곳에 있습니다.

서버 액션DB 트리거
누가 일으키나호출한 코드가 이름으로 부른다테이블에 쓰기만 하면 저절로
누구의 작업에서 실행되나이 함수를 부른 작업에서만그 테이블에 쓰는 모든 작업에서
실제로 나가는 쿼리함수 안에 다 적혀 있다호출부에는 insert 한 줄만 보인다
보낸 값과 저장된 값같다말없이 다를 수 있다
다른 팀원의 PR 에서이 함수를 쓰면 diff 에 드러난다아무 흔적 없이 실행된다

같이 알게 된 트리거의 단점이 몇 가지 더 있는데, 뿌리는 같습니다. 호출하는 쪽이 모른다는 것.

  • 앱이 들고 있는 값이 DB 와 달라진다. 앱이 insert 한 객체에는 origin 이 비어 있는데 DB 에는 채워져 있습니다. RETURNING 으로 다시 읽지 않으면 앱은 끝까지 모릅니다.
  • 트리거가 여러 개면 순서가 또 하나의 숨은 규칙이 된다. PostgreSQL 은 같은 시점의 트리거를 이름 알파벳 순으로 실행합니다. 이름만 바꿔도 동작이 달라질 수 있습니다.
  • 꺼질 수 있다. 데이터를 복사하거나 복구할 때 session_replication_role = replica 로 트리거를 끄는 경우가 있습니다. 그 경로로 들어온 행에는 트리거가 채우는 값이 없습니다.

그래서 어떻게 고쳤나

피드백을 받고 트리거 PR 을 닫았습니다. 그리고 어떻게 고칠지도 같은 피드백에서 방향을 잡았습니다. 트리거로 값을 지어내지 말고, 라이브러리 안내대로 NOT NULL 을 풀라는 것이었습니다.

alter table accounts alter column origin drop not null;

한 줄입니다. 함수와 트리거, 테스트까지 갖춘 처음 PR 보다 훨씬 초라해 보입니다. 그런데 이제 누군가 origin 이 비어 있는 행을 보고 "왜 비어 있지?"라고 물으면, 답이 찾을 수 있는 곳에 있습니다. 라이브러리가 안 보내고, 열 주석과 릴리스 노트 링크가 이유를 말해 줍니다. 값을 지어내는 숨은 로직이 없으니, 숨은 근거를 찾을 일도 없습니다.

물론 비용이 없는 건 아닙니다. 값이 비면 그 열에 걸린 고유 키가 제 역할을 못 하는 경우가 생깁니다. 저는 이 위험을 알고도 이번에는 고유 키를 새로 걸지 않기로 했고, 그 이유를 PR 에 적어 뒀습니다. 고친 것만큼, 고치지 않기로 한 것과 그 이유를 남기는 일도 다음 사람을 위한 일이라고 생각합니다.

트리거를 쓰지 말자는 건 아니다

트리거가 맞는 자리도 있습니다. 누가 어떤 경로로 쓰든 반드시 남아야 하는 변경 이력처럼, 어떤 작업에서 실행되든 그 작업의 결과를 바꾸지 않는 일입니다. 기록을 하나 더 남길 뿐 원래 쿼리가 하려던 일은 그대로 두니, 다른 사람의 작업과 엮여도 문제를 만들지 않습니다.

제가 정한 기준 — 내 로직이 다른 작업에 문제를 만들면 안 된다

이번 일을 한 단어로 줄이면 결합도입니다.

서버 액션에 둔 로직은 그 함수를 부른 작업과만 결합합니다. 누가 이 로직에 기대는지 호출부를 찾으면 다 나오고, 로직을 바꿀 때 영향받는 범위도 거기까지입니다. 결합이 코드에 드러나 있습니다.

트리거에 둔 로직은 그 테이블에 쓰는 모든 작업과 결합합니다. 지금 있는 작업뿐 아니라, 앞으로 다른 팀원이 만들 작업까지요. 그런데 그 결합은 어느 쪽 코드에도 적혀 있지 않습니다. 저는 제 로직에 누가 묶여 있는지 모르고, 묶인 쪽은 자기가 묶여 있다는 걸 모릅니다. 관리자 계정 일괄 등록이 엉뚱한 origin 을 얻게 된 건 그 보이지 않는 결합 때문이었습니다.

그래서 기준을 이렇게 정했습니다.

  1. 내 로직 때문에 다른 작업에 문제가 생기면 안 된다. 내가 만든 로직이 다른 사람의 작업 결과를 바꾼다면, 그건 내 작업의 범위를 넘어선 것이다.
  2. 결합은 드러나 있어야 한다. 누가 내 로직에 기대고 있는지 코드에서 찾을 수 있어야 하고, 기대는 쪽도 자기가 무엇에 기대는지 알 수 있어야 한다.
  3. 결합의 범위는 내가 정할 수 있어야 한다. 부르는 쪽만 묶이는 서버 액션과 달리, 트리거는 앞으로 생길 작업까지 묶는다. 범위를 내가 통제할 수 없는 곳에 판단 로직을 두지 않는다.

마치며

병렬로 일하는 팀에서 제 코드는 제 작업 안에서만 끝나지 않습니다. 그래서 이제는 PR 을 올리기 전에 하나를 더 묻기로 했습니다. "이 로직은 누구와 묶이고, 그 사람의 작업을 망가뜨릴 수 있을까?"
