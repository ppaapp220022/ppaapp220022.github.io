1. GKE — 플랫폼이 하던 일이 선언 파일로

Vercel 에서는 인스턴스 개수, 무중단 배포, 진입 경로, 환경 변수를 플랫폼이 알아서 처리합니다. GKE 에서는 이것들을 매니페스트(원하는 상태를 적은 YAML)에 직접 적습니다.

  • 배포: git push 로 끝나지 않습니다. 이미지를 빌드하고, 어떤 이미지를 띄울지 선언을 바꿔야 반영됩니다.
  • 상태: 파드는 언제든 죽고 새로 생깁니다. 로컬 디스크나 메모리에 둔 것은 사라진다고 가정해야 합니다.
  • 대가: 통제권과 이식성을 얻는 대신 프로브·리소스 한도·로그 수집을 직접 챙겨야 합니다.

2. Redis 대신 Valkey

컨테이너로 Next.js 를 여러 개 띄우면 캐시가 파드마다 따로 생깁니다. 새로고침할 때마다 다른 버전이 보이는 이유입니다. 그래서 캐시를 파드 밖의 공유 저장소로 빼야 하고, 보통 그 자리를 Redis 가 맡습니다.

Valkey 는 Redis 가 2024년에 라이선스를 바꾸자 그 직전 버전을 포크해 Linux Foundation 에서 BSD 라이선스로 이어 가는 프로젝트입니다.

  • 호환성: 프로토콜과 명령이 Redis 와 같습니다. 기존 Redis 클라이언트를 그대로 쓰고 접속 주소만 바꾸면 됩니다.
  • 라이선스: BSD 라 클러스터 안에 직접 띄워도 조건을 따질 필요가 없습니다.
  • 주의: 캐시가 공유되면 무효화도 공유돼야 합니다. 파드를 둘 이상 띄운 상태에서 확인해야 드러나는 문제입니다.

3. Supabase RPC → CNPG + Bun + Drizzle

전 — supabase.rpc('함수명', 인자) 는 PostgREST 의 /rpc/함수명 으로 가는 HTTP 호출입니다. PostgREST 가 토큰을 풀어 요청자를 DB 세션에 실어 주기 때문에 함수 안의 auth.uid() 와 RLS 정책이 동작했습니다.

후 — CNPG 는 DB 가 아니라 쿠버네티스에서 Postgres 를 운영해 주는 오퍼레이터입니다. 엔진은 그대로 Postgres 라 SQL·함수·스키마는 옮겨 갑니다. 서버 코드는 Bun 위에서 Drizzle 로 DB 에 직접 붙습니다.

// 전
const { data, error } = await supabase.rpc('list_items', { p_category: category })

// 후 — 기존 함수 호출
const rows = await db.execute(sql`select * from list_items(${category})`)

// 후 — 쿼리 빌더
const items = await db.select().from(itemsTable).where(eq(itemsTable.category, category))

가장 조심할 곳은 권한입니다. RLS 는 Postgres 기능이라 그대로 쓸 수 있지만, auth.uid() 는 PostgREST 가 채워 주던 값이라 그 계층이 빠지면 동작하지 않습니다. 요청자를 DB 까지 넘기는 경로를 새로 정해야 합니다.

정리

관리형 스택은 기능 목록이 아니라 숨겨진 일의 묶음이었습니다. 옮기고 나면 캐시 공유, 요청자 전달, 오류 모양처럼 계층 사이에 있던 약속들이 하나씩 드러납니다. 엔진이 같으니 코드는 대부분 옮겨 가고, 깨지는 곳은 그 경계입니다.
