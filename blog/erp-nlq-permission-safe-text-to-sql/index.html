AI가 만든 SQL, 믿어도 될까? — ERP 자연어 질의 시스템 기획과 기술 선택

November 11, 2026

들어가며

"ERP에 AI를 붙인다면 무엇을 해야 할까?"에서 시작했습니다.

가장 먼저 떠오른 건 자연어 질의였습니다. "지난달 확정된 주문 몇 건이야?"라고 물으면 AI가 SQL을 만들어 답해 주는 기능입니다. 그런데 이건 이미 많은 도구가 하고 있습니다. 똑같은 걸 하나 더 만드는 건 의미가 없다고 생각했습니다.

그래서 기존 도구들이 놓치고 있는 것을 찾는 데서 기획을 시작했습니다. 이 글은 결과물보다 그 과정, 즉 무엇을 풀기로 했고 왜 이 도구들을 골랐는지에 대한 기록입니다.

  • 레포: github.com/ppaapp220022/erp-nlq
  • 혼자, Claude Code와 짝으로 개발

1. 기획: 무엇을 풀 것인가

정확도가 아니라 권한

text-to-SQL 도구를 살펴보면서 계속 걸렸던 점이 있습니다. 이 도구들은 DB에 SQL을 직접 실행합니다.

ERP 화면에는 권한이 걸려 있습니다. 영업 사원은 자기 주문만 보고, 재고 담당자는 고객 송장을 못 봅니다. 그런데 AI가 만든 SQL을 DB에 바로 돌리면 이 권한이 전부 무시됩니다. 영업 사원이 "전체 매출 알려줘"라고 물으면 남의 주문까지 합친 숫자가 나옵니다.

저는 이게 업무 시스템에 AI를 붙일 때 가장 먼저 막아야 할 문제라고 봤습니다. 정답률이 90%든 95%든, 권한 밖 데이터가 한 번이라도 나오면 회사에서는 쓸 수 없기 때문입니다. 그래서 목표를 한 문장으로 정했습니다.

LLM이 어떤 SQL을 만들어도 사용자 권한 밖의 데이터는 나오지 않게 코드로 강제하고, 정확도와 권한 우회 건수를 같은 평가 세트로 잰다.

뒤 절반도 중요했습니다. "안전하게 만들었다"는 말은 숫자가 없으면 주장일 뿐이라서, 처음부터 측정을 목표에 넣었습니다.

이 프로젝트로 보여 주고 싶은 세 가지

기능을 고를 때 기준이 필요했습니다. 그래서 이 프로젝트로 보여 줄 것을 세 축으로 정하고, 기능을 넣을 때마다 어느 축을 채우는지 확인했습니다.

축보여 줄 것
ERP 도메인 이해업무 흐름과 데이터 구조, 업무 규칙이 애매한 지점을 안다
AI 엔지니어링LLM 기능을 측정하고, 개선하고, 안전하게 만든다
오픈소스 활용오픈소스를 비교해 고르고, 소스를 읽고, 라이선스 경계를 지킨다

예를 들어 "매출이 주문 기준인지 송장 기준인지 되묻는 기능"은 ERP 도메인 축이고, "Odoo 화면 보고서와 내 SQL 결과를 대조하기"도 같은 축입니다. 반대로 멋있어 보여도 어느 축도 채우지 않는 기능은 뺐습니다.

우선순위, 그리고 버리는 기능

혼자 끝까지 가려면 기능에 우선순위를 매기는 것이 먼저였습니다.

  • 1단계 (반드시): 질문 → SQL, 권한 강제, 읽기 전용 실행, 평가 50문항, 화면. 이것만 있어도 결과 표가 나옵니다.
  • 2단계 (차별점): 검색(RAG), 되묻기, RLS 비교, 감사 로그, CI, 기존 도구(WrenAI)와 비교.
  • 3단계 (하지 않음): 결과 마스킹, 로컬 모델 비교, MCP 서버, Odoo 애드온, LoRA.

3단계는 정말 해 보고 싶었던 것들입니다. 집 PC의 GPU로 로컬 모델을 돌리고 LoRA까지 해 보는 계획도 세워 뒀습니다. 하지만 혼자 하면 범위를 넓히고 싶은 유혹이 더 크다는 걸 알았기 때문에, **"결과 표가 나오기 전에는 새 기능을 넣지 않는다"**는 규칙을 먼저 정했습니다. 떠오르는 아이디어는 "2차 목록"에만 적었습니다.

진행은 마일스톤과 점검 기준으로 했습니다. 정해진 날짜를 맞추는 것보다 "앞 단계의 점검을 통과하지 못하면 다음으로 넘어가지 않는다"가 더 중요하다고 생각했습니다. 예를 들어 권한 강제 단계의 점검은 "우회 0건, Odoo 화면과 결과 수 일치"였고, 이걸 통과해야 평가 단계로 넘어갔습니다.

시작하기 전에 정한 규칙

혼자 AI와 짝으로 개발하면, 코드는 빨리 나오지만 기준이 흔들리기 쉽습니다. 그래서 코드를 쓰기 전에 절대 규칙부터 적었습니다.

  1. LLM이 만든 SQL은 신뢰하지 않는다. DB에 닿는 길은 execute() 하나뿐이다.
  2. 질의 계층은 superuser로 접속하지 않는다.
  3. 평가 문항은 프롬프트 예시로 쓰지 않는다. 섞이면 점수가 부풀려진다.
  4. 찾은 우회 경로는 고치기 전에 실패하는 테스트로 먼저 남긴다.

구현은 Claude Code에 많이 맡겼지만, 이 규칙과 "끝났다"의 기준은 제가 정하고 지켰습니다. 리뷰어가 없는 혼자 하는 프로젝트라 작업 하나 = 브랜치 하나 = PR 하나로 끊고, PR마다 자동 테스트와 AI 코드 리뷰를 통과해야 머지되게 했습니다. 이 방식은 기획 단계에서 "혼자 할 때 리뷰를 무엇으로 대신할까"를 고민하다 정한 것입니다.

Odoo — 프레임워크를 배우러 온 게 아니니까

처음에는 ERPNext를 쓰려고 했습니다. 그런데 ERPNext는 Frappe 프레임워크 위에서 돌아서, 데이터를 제대로 읽으려면 DocType, tab 접두사 테이블, Frappe 권한 모델부터 배워야 했습니다. 이 프로젝트의 목표는 ERP 데이터 위에 질의 계층을 만드는 것이지 새 프레임워크를 익히는 게 아니었습니다.

결정적이었던 건 DB입니다. ERPNext는 MariaDB를 쓰는데, Odoo는 PostgreSQL을 씁니다. PostgreSQL이면 검색은 pgvector로 붙일 수 있고, 무엇보다 권한 강제를 두 가지 방식(SQL 재작성과 Postgres RLS)으로 구현해서 비교할 수 있었습니다. MariaDB였다면 비교 실험이 하나로 줄었을 겁니다.

Dolibarr도 봤지만, 권한을 PHP 코드 안에서 확인하는 구조라 "담당자가 본인이거나 없는 주문" 같은 행 단위 규칙이 DB에 남아 있지 않았습니다. 저는 Odoo의 권한 규칙(Record Rules)을 읽고 그대로 코드로 옮길 계획이었기 때문에, 규칙이 데이터로 남아 있는 Odoo가 맞았습니다.

그리고 Odoo 코드는 한 줄도 수정하지 않기로 했습니다. 공식 Docker 이미지를 그대로 띄우고, DB에는 읽기 전용 역할과 RLS 정책만 더했습니다. 라이선스(LGPL) 경계를 깔끔하게 지키고 싶었고, "기존 시스템을 건드리지 않고 위에 얹는다"는 게 실제 회사에서도 받아들여지기 쉬운 방식이라고 생각했습니다.

Python 하나로 — 혼자니까 언어를 나누지 않는다

백엔드는 Python 하나로 갔습니다. SQL 파서(sqlglot), 평가 도구, 임베딩, WrenAI 비교가 전부 Python 생태계에 있었습니다. 팀이라면 몰라도 혼자서는 언어를 나누지 않는 편이 훨씬 빠릅니다. API는 FastAPI로 얇게 감쌌고, 패키지 관리는 uv로 해서 설치와 버전 고정을 단순하게 했습니다.

처음부터 함수 경계를 generate(question, user) → sql과 execute(sql, user) → rows 둘로 정했습니다. 터미널, 평가, 화면이 모두 이 두 함수만 부릅니다. 나중에 API로 감쌀 때도 그대로 썼습니다.

sqlglot — "다시 쓸 수 있는" 파서

권한 강제의 핵심은 AI가 만든 SQL을 구문 트리로 읽고, 권한이 걸린 테이블을 권한 조건이 붙은 서브쿼리로 바꿔 끼우는 것입니다.

-- AI가 만든 SQL
SELECT count(*) FROM sale_order WHERE state = 'sale';

-- 실제로 실행되는 SQL (영업 사원 7번)
SELECT count(*)
FROM (
  SELECT * FROM sale_order
  WHERE company_id IN (1)
    AND (user_id = 7 OR user_id IS NULL)
) AS sale_order
WHERE state = 'sale';

그러려면 파서가 네 가지를 해야 했습니다. Postgres 문법을 읽고, 트리를 고치고, 고친 트리를 다시 SQL로 내고, 설치가 단순해야 합니다.

  • sqlparse는 토큰을 나누는 수준이라 FROM 절의 테이블을 빠짐없이 찾는다는 보장이 없었습니다. 권한에 쓰기엔 위험합니다.
  • pglast는 Postgres 실제 파서라 가장 정확하지만, 트리가 Postgres 내부 구조 그대로라 재작성 코드가 길어지고 C 확장이라 빌드를 탑니다.
  • sqlglot은 네 가지를 다 갖췄습니다.

대신 sqlglot은 Postgres 실제 파서가 아니라는 약점이 있습니다. 그래서 모르는 구문은 거부하게 하고, DB 쪽 RLS가 같은 규칙을 한 번 더 걸게 했습니다. 또 guard는 sqlglot이 다시 만든 SQL을 실행하기 때문에, 버전이 바뀌면 실행되는 SQL도 바뀔 수 있습니다. 그래서 sqlglot 버전은 범위가 아니라 정확한 버전으로 고정했습니다.

Claude API — 개발은 Haiku, 측정은 Opus

평가를 매번 비싼 모델로 돌리면 비용이 금방 늘어납니다. 그래서 기획 단계에서 모델 배치를 먼저 정했습니다.

  • 개발과 CI(PR마다 20문항)는 Haiku
  • 결과 표에 들어갈 측정은 Opus
  • 두 점수는 절대 섞지 않는다. 결과에는 어떤 모델로 잰 숫자인지 항상 적는다.

원래는 반복 개발을 집 PC의 로컬 모델로 돌릴 계획이었습니다. 하지만 "프롬프트를 로컬 모델에 맞춰 다듬으면 Claude에서 다르게 동작할 수 있다"는 점이 마음에 걸렸고, Haiku가 충분히 싸서 로컬 모델 비교는 3단계로 미뤘습니다.

WrenAI — 고르는 게 아니라 견주는 대상

"내가 만든 게 기존 도구보다 나은가"를 보여 주려면 비교 대상이 필요했습니다. Vanna는 예시를 검색해 넣는 방식이라 제가 따로 재는 RAG와 겹쳤고, LangChain SQL 에이전트는 라이브러리 조각이라 "도구 하나와 비교"가 되지 않았습니다. 의미 계층을 두는 WrenAI가 접근이 가장 달라서 비교할 거리가 많다고 판단했습니다.

WrenAI 코드는 레포에 넣지 않고 별도 컨테이너로만 띄웠습니다. 일부가 AGPL이라 라이선스 경계를 지키기 위해서입니다.

3. 결과: 기획한 대로 된 것

50문항 평가 세트(판매·구매·재고·회계)를 만들고, 문항마다 누가 묻는지를 정해 그 사람 권한으로 채점했습니다.

  • 정답률: 프롬프트만 썼을 때 41개 → 최종 49개 (Haiku, 3회 평균)
  • 권한: Odoo 화면과 행 수 84/84 일치, 우회 0건
  • WrenAI와 비교: WrenAI는 27개 정답에 영업 사원 질문 15개 중 약 9개에서 남의 데이터가 섞였습니다. 그런데 WrenAI가 만든 SQL을 제 execute()로 실행하면 우회가 0이 됐습니다.

마지막 결과가 이 프로젝트에서 가장 마음에 드는 숫자입니다. 권한을 AI에 맡기지 않고 실행 단계에서 강제한다는 기획의 핵심이, 다른 도구가 만든 SQL에서도 그대로 통한다는 뜻이기 때문입니다.

4. 생각이 바뀐 것

기획과 실제가 다른 지점도 있었습니다. 저는 이 부분이 가장 많이 배운 곳이라고 생각합니다.

RAG가 답일 줄 알았습니다. 비슷한 질문-SQL 예시를 검색해 넣으면 정답률이 크게 오를 거라 기대했는데, 41.0 → 41.7로 거의 변화가 없었습니다. 효과가 컸던 건 "매출은 송장 기준, 환불 차감, 부가세 제외"처럼 업무 지식을 정리해 넣은 것이었습니다(→ 45.7). 회계 영역에서 특히 차이가 컸습니다. 예시는 "어떻게 쓰는지"를 알려 주지만, "무엇이 맞는지"는 업무 지식이 알려 준다는 걸 숫자로 확인했습니다. 세 축 중 "ERP 도메인 이해"를 넣은 게 맞았다고 느낀 순간이었습니다.

큰 모델이 답일 줄 알았습니다. 최종 구성을 Opus로 재 보니 47/50으로, Haiku(48~49)와 차이가 없었습니다. 병목은 모델이 아니라 지식이었습니다.

되묻기는 기획보다 중요했습니다. 처음에는 2단계의 부가 기능 정도로 생각했는데, "주문 기준인가요, 송장 기준인가요?"처럼 기준이 갈리는 질문에서 되묻게 하니 마지막 몇 문항이 풀렸습니다. 기준이 정해진 질문에서는 150번 중 한 번도 되묻지 않았기 때문에, 쓸데없이 묻지도 않았습니다.

마치며

이 프로젝트에서 가장 어려웠던 건 구현이 아니라 기획이었습니다. "ERP에 AI를"이라는 넓은 주제를 혼자 끝낼 수 있는 크기로 좁히고, 그 안에서 **"정확도보다 권한"**이라는 차별점을 찾는 데 가장 오래 걸렸습니다.

그리고 도구를 고를 때마다 "왜 이걸 쓰는가"를 한 문장으로 말할 수 있을 때까지 비교했습니다. Odoo는 PostgreSQL이라서, sqlglot은 다시 쓸 수 있어서, Python은 혼자라서, Haiku와 Opus는 비용과 측정을 나누기 위해서. 이렇게 이유를 적어 두니 나중에 결과가 기대와 다를 때도 어디서 판단이 틀렸는지 돌아볼 수 있었습니다.

마지막으로, 맞는 SQL과 믿어도 되는 SQL은 다른 문제라는 걸 배웠습니다. 업무 시스템에 AI를 붙일 때 무엇을 AI에 맡기고 무엇을 코드로 막아야 하는지, 그 경계를 정하는 일이 앞으로도 제가 가장 신경 써야 할 부분이라고 생각합니다.
